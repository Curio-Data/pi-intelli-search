# Batch Research Study Protocols

Execution protocol for [Phase 4](BATCH-RESEARCH.md#phase-4-guidance-documentation-and-live-evidence), based on `650f835`. On 17 November 2026 the owner authorised both studies using the existing OpenRouter credential, with no dollar cap and actual spend reported at the end. The timing study measures the tool; the effectiveness study measures the agent's whole task, including its decision not to batch. Neither estimates an effect for all topics or hosts.

## Timing and Pool Size

**Comparison.** For each size N, measure one independent batch, one expansion batch and the same N single queries run one after another on native `Pi`. Use a direct host call with exact arguments, not an agent loop. For singles, measure the sum of the N tool-execution intervals, not the sum of N host startup times. Start each arm with an empty workspace and index, retain the same workspace across its N singles, and keep cache suggestion enabled: the difference in suggestion work is part of the feature. One process and key active at a time, no other studies or E2E jobs. Use a 30-minute tool deadline and a 20-second gap **between arms only**; exclude gaps from latency.

**Corpus.** Use the first 2, 5 or 10 rows, in order. Pass the query and focus columns verbatim, `domains: ["sqlite.org"]` and `maxUrls: 5` for every entry in every arm. These public questions concern [_SQLite_](https://sqlite.org/) reliability; they were not drawn from client conversations.

| ID | Query | Extraction Focus |
|---|---|---|
| 1 | SQLite WAL reader snapshots | When does a reader's snapshot change? |
| 2 | SQLite WAL checkpoint starvation | Explain the effect of long-lived readers and how to detect incomplete checkpoints. |
| 3 | SQLite synchronous FULL versus NORMAL in WAL mode | Distinguish consistency from loss of recent commits after a power failure. |
| 4 | SQLite busy timeout and writer contention | Identify when waiting helps and when an operation still returns busy. |
| 5 | SQLite online backup API and concurrent writes | Explain snapshot consistency and what happens when the source changes. |
| 6 | SQLite rollback journal crash recovery | Identify the conditions for a hot journal and when recovery occurs. |
| 7 | SQLite foreign key enforcement per connection | State when enforcement must be enabled and how to check it. |
| 8 | SQLite immediate versus deferred transactions | Compare when writer access is acquired and which operations can fail. |
| 9 | SQLite integrity_check and foreign_key_check | Distinguish the checks and the meaning of their results. |
| 10 | SQLite atomic commit across attached databases | Identify journal-mode and main-database conditions on atomic commit. |

**Arms and repetitions.** For each N run S (singles), I8 (independent, eight extraction slots) and E8 (expansion, eight slots). At N=5 and 10 also run I4 and I16. At N=2 at most ten pages can be extracted, so do not present a sixteen-slot saturation comparison there. Use two blocks per size, one in order S, I4, I8, I16, E8 (omit I4 and I16 at N=2) and one in reverse; order sizes 2, 5, 10 in block one, 10, 5, 2 in block two. This is 26 arms, 34 single calls and 20 batch calls, covering 162 entry pipelines and six planned merges. The I and E suffix is `batchExtractionConcurrency`; S uses four extraction slots. I8/S measures the shipped batch configuration, including its larger pool, not the isolated effect of batching. I4/S is the matched-slot comparison, available only at N=5 and 10. Do not rerun failures or stop early for favourable times. Keep normal internal retries. Retain sizes' separate results because subsets overlap. At N=5 and 10, four entries at once supply up to twenty pages per wave, not necessarily twenty simultaneously ready extractions. Do not infer a plateau if the higher pool never had demand.

**Observations.** Use an opt-in, allowlisted study selection in `test/run-e2e-parallel.sh` in sequential mode, not its default whole-suite launch. Build a single-attempt study path: the existing scenario list is fixed, the direct batch wrapper defaults to 600 seconds, and the outer runner defaults to 1,200. Test a 1,800-second deadline per tool and an outer watchdog allowing at least that duration per call in the arm plus startup, teardown and trace flush. Record censored durations separately. Freeze effective stage models, retries, budgets, pacing, host version and `batchConcurrency=4`, `extractionConcurrency=4`. Pin stage models to `openrouter/perplexity/sonar` and `openrouter/minimax/minimax-m3` (extract and collate). Capture start/end of tool execution, attempt lifetimes, HTTP and streamed 402/429 responses, routes, fetched and extracted page counts, merge outcome, input/output characters, rejected candidates, and per-member reports. Test merge classification with both actual system prompts: their first lines match in `src/core/prompts.ts`. Use their distinct full identities, not the shared prefix used by `test/e2e/trace-extension.mjs`. Derive peak active extraction attempts by matching start/end IDs; add study-only enqueue, acquire, release and abort events with entry/page identifiers to measure semaphore waiters. A permit held across a retry or throttle is not necessarily an active provider request. Compare the URLs in successful extraction inventories for singles and batches; distinguish those from all successful fetches, because singles lack `stages.fetch.urls`. Compare actual merge prompt tokens, if available, with the configured input budget as a reference, not an enforced bound. Inspect each accepted merge's contradiction/gap items against its member summaries and source pages; mask run and block IDs and record the item, relevant summary passage and source passage. Score supported when the summaries substantiate the disagreement or gap, insufficient detail when the sources substantiate it but the summaries do not, and unsupported otherwise. Mark unavailable evidence unknown, not unsupported. No disagreements found is not proof summaries always suffice.

Report every assigned arm's elapsed time, completion counts, costs and failure flags first, including missed or stopped arms. As a secondary description, show within-block `T(batch)/sum(T(single))` and fixed-N pool contrasts for pairs with every entry and required merge completed. Flag differences in per-entry extracted page counts and URLs; report matched-count subsets, exclusions and the range across blocks rather than a pooled average. Show workload differences, including how many pages were actually used. Keep current defaults if comparisons disagree across blocks or either pool lacks demand; two blocks cannot establish an optimum or an error rate of zero.

## Agent Effectiveness

**Treatment.** Use `openrouter/openai/gpt-6.2-sol` in the native headless agent loop for all 12 sessions. The available arm gets the shipped batch declaration and guidance; the unavailable arm uses the same core behind the pre-batch single-query declaration and guidance, rejects raw `queries` before execution, and exposes no batch skill text. Take the single-query declaration and guidance from `67a5eb5` and archive a field-level diff of what the model sees in both arms. Do not compare wholly different releases. Use an identical tool allowlist (research and a workspace-confined cache read), host version, main-model reasoning settings, search/extract/collate models, input and output caps. No shell, host web tools, memory, prior sessions, other skills or repository context. Agents can answer without a call. Restrict both arms to four entry pipelines and three pages per entry per task, not four tool calls: a batch counts once for calls but N times for the work budget. Enforce the limit before dispatch and log rejected attempts. Set a common 20-minute session deadline and eight main-model turns. Set `defaultUrls=maxUrls=3` and `maxBatchEntries=4`. Use identical budget and invalid-argument messages for shared rules. Test the study-only reader against absolute paths, traversal and symlinks outside the cache. Use a single-attempt driver, not `e2e_run_pi`, which can retry three times. Block the ninth main turn and over-budget entries before the relevant provider call. Run one session at a time, each with an empty workspace and cache. The study is of a research-only environment, not general agent tool selection.

**Task A, planned questions (verbatim).** “Prepare a short maintenance checklist for a SQLite database. Explain when to enable foreign key enforcement, how to check existing foreign key violations, what integrity_check establishes, and how an online backup differs from copying an active database file. Give a practical check or action for each and cite official documentation.”

**Task B, multi-part synthesis (verbatim).** “A SQLite service in WAL mode has one writer and long-running read transactions. Its WAL file sometimes grows even though automatic checkpoints are enabled. Explain how the reader can keep a consistent view while writes continue, why checkpoints do not always reclaim space, and what an operator can safely change. Distinguish a larger file from a failed commit, and cite official documentation.”

Run three matched pairs per task. In replicate order use A off/on then B on/off; B off/on then A on/off; A off/on then B on/off. Prompts never request batching, a minimum call count or a particular decomposition. Record actual adoption, mode, calls and member counts. All assigned sessions count even if the model does not batch, makes a bad call or times out. No replacement sessions. Three replicates per task balance order across tasks but not within either task. Before freeze verify provider cache isolation or a documented expiry and sufficient inter-session gap; otherwise retain observed cache hits and order as confounds and do not attribute net timing or billed-input differences to batching alone.

**Frozen rubric.** Score four task-specific items, each 0 (missing or materially wrong), 1 (correct but incomplete or unsupported by the cited official page), or 2 (correct, actionable and supported by a relevant official citation). A: per-connection enablement outside an active transaction; `foreign_key_check` and the meaning of returned rows; `integrity_check`'s scope and its exclusion of foreign keys; a consistent backup of live data rather than relying on copying a changing main file alone. B: stable reader end mark plus writers appending; checkpoints cannot pass the oldest relevant reader boundary; a practical mitigation with its trade-off (shorten read transactions or schedule an appropriate checkpoint without promising immediate truncation); distinguish WAL reuse/size from commit failure and identify a relevant observable such as checkpoint progress. Sum 0 to 8. Flag materially unsafe advice independently of score (for example deleting a live WAL file). A session ending without a final answer scores zero on every item. Freeze dated official reference passages and a scoring key before the first session, inaccessible to study agents. A human grader, blind to condition, uses randomly labelled final answers and the same references, with no traces or timings. Use identical grading forms for missing answers. Strip tool metadata and explicit tool or mode labels, retaining substantive claims and citations. Record the grader's condition guess and reason for each answer; do not assume masking succeeded. Freeze all scores before revealing assignments.

**Metrics and interpretation.** Count starts of `intelli_research` once per call ID (separately count rejected attempts, entries and cache reads); turns are completed assistant messages including the final one. Sum main-model input across requests, separating uncached input, cache reads and writes according to verified host/provider accounting; never substitute characters or count pipeline model usage. Keep the raw request and assistant message IDs plus input, cache, output and charge fields; the existing evidence analyser drops usage. Test cached, duplicated and missing events offline. Report uncached input separately from total input exposure; neither is interchangeable with billed cost. Flag missing usage rather than treating it as zero. Wall time runs from prompt submission to final answer or deadline, including all tool waits. Report six paired differences per metric, each task's median and all failure flags. Report nominal efficiency only alongside answer quality: describe cost/time reductions without observed quality loss only where complete pairs show both, with no new unsafe answer. This small live study cannot establish non-inferiority. Live search and routing variation, repeated tasks and possible recognition of formatting by the grader limit interpretation.

## Design Review

On 17 November 2026 two independent Herdr reviewers evaluated both protocols. Claude Code (`claude-opus-5-5`) recommended approval with changes for both; `Pi` (`kimi-coding/k3.1-pro`) recommended revision before freezing either. Their reports, the reviewed draft and model provenance are in `evidence/agents/2026-11-17-batch-study-review/`. The revisions retain the 26-arm and 12-session designs, qualify the unmatched pool and session order, and make the trace, runner, accounting and masking checks prerequisites. Both reviewers then checked the revised protocols and found no design blocker to offline preparation. Review of the design does not establish that these checks have been implemented or passed.

## Cost and Release Gates

Using the [repository cost assumptions](../../README.md#cost), one five-page entry costs ≈$0.052 before unusual retries; 162 entries cost ≈$8.46, plus six variable-size merges. This is a planning estimate, not a maximum. The draft proposed separate ceilings of $15 and $12; the owner waived both. The effectiveness pipeline has at most 48 three-page entries (≈$1.84 before merges and retries); report main-model charges, including cached inputs, separately from the pipeline. No paid judging. Do not substitute cheaper models or silently reduce the matrix.

Before spending, freeze a manifest with exact builds, prompts, reference passages, ordering, configuration and measurement code hashes. Prove offline that only scheduled arms launch, telemetry is complete or explicitly missing, the unavailable arm neither advertises nor executes batches, the grader receives only masked final answers, and the study guards enforce the entry, page and turn limits. Attribute actual charges to the individual provider requests, including retries and failed attempts. A shared key's total usage delta is a cross-check, not study spend. Stop on a 402 or failed trace capture and flag unknown charges rather than treating them as zero. Retain 429 signals with normal bounded retries and keep redacted records on the encrypted drive. Nothing in these protocols changes a shipping default or authorises release.

## Recorded Outcomes

Collection finished on 18 November 2026. The [public benchmark](../BENCHMARKS.md#batch-research-on-the-native-host) separates the direct-tool measurements from the later five-query agent comparison. The timing study completed 160 of 162 entry pipelines across all 26 scheduled runs. Its traces recorded no 402 or 429 responses. This observation applies to this provider account and workload, not to a general rate limit.

All six expansion runs produced reports. Merge requests used 3,898 to 4,361 prompt tokens at two entries, 9,047 to 9,066 at five and 17,607 to 18,931 at ten. All were below the 221,000-token collation input budget used for comparison. An agent reviewed the six masked reports against their member summaries and cached official documentation. The summaries preserved enough detail to identify differences, but the merge sometimes presented differences in scope as contradictions. For example, it contrasted a backup wrapper that blocks writers with the native library's shorter lock during a backup step. Both behaviours can coexist. The masked review also questioned source numbers, but its packet omitted the merged source inventories. A check against the original inventory confirmed that the wrapper citation points to the wrapper documentation and distinguishes it from the native library sources. A valid source number does not by itself establish that a source supports a claim. The runs do not show that reading extraction files would correct the interpretation. The branch keeps the summary-only merge.

All 12 agent sessions produced answers. The table gives the median of the three within-task differences, batch available minus batch unavailable. It compares availability, whether or not the agent used a batch. Positive elapsed time means the batch-enabled sessions took longer. Provider cache isolation was not verified.

| Maintenance checklist (A) | −1 | −1 | −28 | +26.6 |
| Checkpoint synthesis (B) | 0 | 0 | +750 | +6.6 |

Research Calls counts attempts. On task A, one call in each condition exceeded the three-page limit and was rejected before execution. Counting only admitted calls gives a median difference of zero.

At closeout, a fresh agent rather than the originally proposed human grader scored the anonymised answers against the frozen eight-point rubric before the coordinator joined scores to assignments. On task A, all three batch-enabled answers scored seven; the three without batching scored seven, seven and eight. The difference was detail about the rows returned by `foreign_key_check`. All six task B answers scored eight. The grader flagged no unsafe advice and guessed “batch available” for all 12 answers; the guesses did not distinguish the conditions. These observations do not establish an effect on quality.

The timing study's 1,159 provider generations cost $4.515534. The 12 agent sessions' 24 main-model generations cost $0.1787607. Together these are a verified subtotal of $4.6942947, not a total: the agent sessions did not retain identifiable research-pipeline receipts. The later five-query pair has its own main-model charges in the public benchmark and is excluded from this subtotal. A shared key's balance change cannot assign the missing charges to these sessions.

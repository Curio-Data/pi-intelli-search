# Integrated 0.25.0 Release Gates

These gates are historical: 0.25.0 is published and merged. For new work, start at the [post-release handover](HANDOVER.md#resume-here).

On 22 November 2026 the owner included the citation-numbering fix, the `Pi` 1.6.0 retry update and the [_DeepSeek Harness_](https://github.com/deepseek-ai/deepseek-harness) bundle in one release. Use `release/0.25.0` for integration. Keep unpublished pins off `main`. Earlier host receipts identify local builds, not public packages, even when a version string matches.

1. **Qualify the combined tree.** Check the manifests, generated files, dependency audit, builds, deterministic tests, independent tarball installs and bundle inventory. Run the full live suite with owner approval; scenarios 01 to 18 must pass without skips. Export `DSH_BIN` and put isolated pnpm on `PATH` for scenario 18. Scenario 19 is separate and requires its own spend approval. Obtain two independent reviews of the *whole* candidate at one commit, reconcile findings, and verify the amendments. Check changelog dates on the release day. Require green push CI on the exact release commit before staging.
2. **Release the two engine packages.** With explicit owner approval for both, create `mcp-v0.25.0` followed by `pi-v0.25.0` on that commit. The owner approves both stages on npm. Check registry identity and provenance, native installation and the Claude Code and Codex registry installations. Do not stage or announce the dsh plugin at this point.
3. **Test the production launcher before bootstrap.** Start from a clean checkout of the reviewed commit. Pack `plugins/dsh` with `npm pack --json` into a separate output directory, without changing the registry launcher. Retain the tarball, SHA-256, npm integrity and inventory; require the patch, registrar, skill and licence, and no `vendor` files. Verify that the matching public MCP version resolves. With a fresh home, profile, project directory and empty npm and pnpm caches, install the retained tarball with `dsh plugin --profile <name> add <absolute-tarball-path>`. Check the composed configuration for the exact MCP pin and `--host dsh`. Time the first connection on rc.1 against its 60-second discovery timeout. Verify the four `mcp__intelli__*` tools and the installed skill in the running profile (use the inspector from scenario 18). Run the exact public CLI with `--host dsh --check-config` in the project. Remove and reinstall the plugin. Record the host, package identities, cache isolation, checks and timing. Neither `npm view` nor the vendored scenario 18 substitutes for this gate.
4. **Review before publishing dsh.** Give two fresh reviewers the same commit, retained evidence and whole-branch brief, including install instructions and the prominence and accuracy of the README. Resolve findings before the owner bootstrap. If the bundle bytes change, repack and repeat the production-launcher checks. Do not edit the frozen native or MCP tarballs; a change needed inside either requires a new package version.
5. **Bootstrap, verify by name, then promote.** The owner publishes the exact verified tarball with `npm publish <absolute-tarball-path> --access public`, then binds the trusted publisher for subsequent dsh releases. Do not trigger a first `dsh-v*` GitHub Release. Compare registry integrity to the retained pack. Repeat the clean-profile check using `dsh plugin --profile tui add @curio-data/dsh-intelli-search` with no version or local path, including removal and reinstallation. A cited public search requires separate spend approval. Record public evidence separately from local-bundle and pre-bootstrap evidence. Only after this gate promote the verified route at the top of the repository and in release notes, then seek approval to merge.

Stop at the first failed gate. Keep the evidence, withhold the next publication or merge and identify which artifact needs correction. Never reuse an already published version.

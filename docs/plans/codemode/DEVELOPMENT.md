## Operation Runtime and Generation Lifetimes

The next coordinator-owned P4 slice adds `src/core/operation-runtime.ts`. Each invocation captures a lease before service construction or preflight and receives its own ledger and run store, with the runtime's authoritative coordinator and clock. A tracked parent holds the lease across the complete stage chain and store cleanup, including gaps with no active permit. The body must finish late drain and finalisation before returning; the runtime then awaits store and lease settlement. Fetch and store factories remain injected. This slice neither selects the persistence implementation nor integrates its readers or writers.

The generation manager stops old admissions synchronously, aborts and drains the captured runtime, then constructs the successor. Waiting calls honour their own cancellation and follow the latest replacement even if a superseded construction fails. Superseded generations cannot admit work. Captured-generation shutdown cannot close a successor; terminal factory disposal separately stops pending replacement. Invalid replacement settings deliberately leave the old generation closed until a valid replacement arrives. Each adapter must retain that fail-closed choice or explicitly validate settings before requesting replacement.

Progress delivery rejects foreign or settled events, suppresses delivery during generation close and contains renderer failures. Diagnostics belong to the operation rather than the widget generation, so their sink remains usable during close. Registered adapters must supply an operation-owned, user-interface-safe sink that never writes to the raw console. Cleanup failure preserves the original operation error object when both fail, including any attached partial data. Abort conversion retains the caller's reason where available. These are deterministic helper proofs, not actual native session lifecycle, MCP protocol, real-adapter cancellation or widget proofs.
